# CLIVE Identity and Home Surface

**Status:** ACTIVE OWNER DIRECTION
**Date:** 2026-09-21
**Scope:** product name, acronym, startup identity, home surface, orb role, persistent-state presentation

This document records the owner-approved identity and home-surface direction developed while reviewing the current mobile interface. It extends the Intent-to-Execution and Live Experience doctrines. It does not prescribe one permanent visual layout.

## 1. Product identity

The user-facing product identity is **CLIVE**.

Current acronym expansion:

> **Computer Language Interface Virtual Environment**

Use **CLIVE** as the primary brand in the application shell, launch identity and product-facing interaction. The acronym is supporting identity/lore and should not be repeated as constant interface chrome.

CROOKS remains an important operating environment/business context for the current deployment. It should not force CLIVE's long-term identity to remain a CROOKS-branded dashboard.

## 2. Home is not an empty assistant state

The home surface must not conceptually reset to:

> SYSTEM READY
> What do you need?

CLIVE is persistent. When useful operational state exists, opening CLIVE should project the most relevant current objectives, changes, commitments, exceptions and unfinished work.

A quiet/empty surface is valid when nothing deserves attention. Empty UI must result from low information value, not from forgetting the world between conversations.

## 3. Home is a projection of world state, not a dashboard

The home surface should be generated from current operational significance.

It may show:
- a blocking objective;
- a material change;
- an unresolved exception;
- work currently progressing;
- a commitment approaching relevance;
- an important result;
- nothing beyond CLIVE's presence when no information earns space.

It should not become a fixed collection of permanent business cards merely because cards are convenient UI.

The durable model is:

> persistent world/objective state → significance/information gain → smallest useful scene

not:

> modules → dashboard widgets → user chooses where to look

## 4. The orb represents CLIVE's presence

The orb remains a core identity object, but it is not merely a giant microphone button.

It should communicate CLIVE's presence and interaction state:
- quiet/alive while idle;
- responsive while listening/hearing;
- visibly active while investigating/working;
- a coherent source while speaking/responding.

When information becomes more important than presence, the orb may contract, reposition or become secondary so useful evidence gets the space.

Voice is a path into CLIVE, not the definition of CLIVE.

## 5. Health is contextual

Permanent SHOPIFY / GMAIL / VOICE / CHANGES status on the main idle surface is implementation plumbing.

Service/capability health should become prominent when it changes the current objective. Example: Gmail being unavailable matters while checking an unanswered supplier email; it does not deserve prime home-screen space while investigating stock.

Detailed diagnostics remain available separately.

## 6. Navigation should not expose internal architecture

The user should not have to navigate CLIVE as a set of implementation modules or manually choose concurrency modes.

Fixed shortcuts may survive where they provide genuine low-effort value, but they must not define the information architecture.

User-facing Split/Half/Merge/Close remains retired under DEC-050.

## 7. Response-driven scenes

The same home surface can transform as an objective becomes foreground work.

Example:
- home projects a launch blocker;
- owner asks "what's going on with the drop?";
- CLIVE resolves relevant stock, photography, campaign and email work concurrently;
- useful evidence appears progressively;
- the scene becomes a release-readiness view because that is what the objective currently requires.

There need not be a permanently coded "Drop Status screen."

## 8. Startup identity

Approved conceptual startup direction:

1. near-black field / point of light;
2. emergence of an abstract world/intelligence orb;
3. reveal of the acronym:
   - C — Computer
   - L — Language
   - I — Interface
   - V — Virtual
   - E — Environment
4. convergence into the final **CLIVE** wordmark.

This is a brand/experience direction, not a requirement to preserve one generated animation asset forever.

Quality target: restrained, premium, dark, precise, cinematic, high-resolution and typography-led. Avoid generic gaming HUDs, excessive particles/glow and decorative "AI" clutter.

## 9. Design filter

Before adding anything persistent to the primary CLIVE surface, ask:

1. Does this communicate operationally valuable state right now?
2. Would CLIVE still show it if the underlying provider/API were replaced?
3. Is this exposing an internal mechanism the owner should not have to manage?
4. Is it worth the attention and screen area it consumes?
5. Could the same objective be communicated more directly with less UI?

The home surface exists to reduce coordination and attention, not centralise application chrome.
