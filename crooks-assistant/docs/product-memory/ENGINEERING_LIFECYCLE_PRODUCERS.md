# Engineering Lifecycle Producers

Status: repository-only contract and implementation. This document authorises no deployment, no watcher, systemd or runtime change, no business write and no owner-only decision. It describes how CLIVE authors and persists its engineering lifecycle so that stages are read from records rather than inferred from processes.

Code: `app/orchestrator/lifecycle.py` (records, store, kernel, projection) and `scripts/engineering_kernel.py` (the verbs from a shell). Reuses, unchanged: `EngineeringTask`, `TaskRuntimeState`, `EngineeringResult`, `JsonRecordStore`, `evaluate_obvious_continuation`, `evaluate_review_eligibility`, `ReviewEvidence`, `evaluate_review_acceptance`, `gate_review_result`, `build_active_state`.

## Why

Objective E showed the observation path working and the write side missing: ASSIGNED, accepted and COMPLETE were not derivable because nothing authoritative recorded them, and a finished worker looked exactly like an abandoned one. This layer is the smallest producer that closes that gap without adding a scheduler, a service or a second source of truth.

## Records

All records are `StrictRecord`s (unknown fields refused, frozen) under one store root, the `engineering/` directory:

| Record | Path | Mutability | What it proves |
| --- | --- | --- | --- |
| `EngineeringTask` (existing) | `tasks/<task>.r<rev>.json` | immutable | an authorised objective at an exact base SHA |
| `TaskRuntimeState` (existing) | `task-state/<task>.r<rev>.json` | compare-and-swap on `transition_seq` | the current stage, attempt and worker |
| `Attempt` | `attempts/<task>/<attempt>.json` | immutable | assignment, lease duration, monotonic fencing token, the dispatch identity (principal, session, workspace) the kernel recorded |
| `AttemptEvent` | `events/<task>/<attempt>.jsonl` | append-only, `seq` must be the next | opened, acknowledged, heartbeat, progress, evidence (name + digest), candidate, review dispatched, verdict admitted/refused, accepted, integrated, cancelled, blocked, resumed |
| `EngineeringResult` (existing) | `results/<task>/<attempt>.json` | immutable | the candidate: exact result SHA, changed paths, evidence claimed, clean worktree, next action |
| `ReviewDispatch` | `reviews/<task>/<attempt>/dispatch.N.json` + `.packet.md` | immutable | the exact candidate handed to a named reviewer principal, with the packet's digest and bytes |
| `VerdictAdmission` | `reviews/<task>/<attempt>/verdict.N.json` + `.evidence.txt` | immutable | one submitted verdict (`ReviewEvidence`), the kernel's outcome, every reason, and the verdict bytes |
| `Acceptance` | `acceptances/<task>/<attempt>.json` | immutable | READY from an eligible reviewer at the exact candidate |
| `OwnerResolution` | `owner-resolutions/<task>.r<rev>.<seq>.json` | immutable | the owner judgment that lifted an owner gate, as a trusted owner authority adapter verified it: the judgment id, the ledger file and its digest, the owner principal and session, the decision and reason code, and the gate's proposal id and fingerprint. **No verb of this kernel writes it**: the repository-only kernel cannot verify owner origin, so it never lifts an owner gate; the record is the contract for the adapter that will |
| `Integration` | `integrations/<task>.r<rev>.json` | immutable | accepted SHA landed on the target ref: ancestry verified; the target base an ancestor; the target ref resolved to the integration SHA (`remote_head_sha` or `local_head_sha`); for anything but a fast-forward, the accepted integration candidate the result *is* (`integration_candidate`) |
| `ActiveState` (existing) | `ACTIVE_STATE.json` | regenerated by every verb | the Phase 1 projection, unchanged |

When the store root lives inside a git checkout, every verb journals its write as one commit authored by "CLIVE kernel" naming the operator. Git remains the auditable source of record; the store is restart-safe because nothing is held in memory and every derived value (lease state, stage) is recomputed from the files.

## One writer, whole records

Every verb runs as one guarded unit:

- **The writer lock.** The verb holds an exclusive advisory lock on `<store>/.kernel.lock` (an empty file the layout creates and the journal commits once; `flock`) from before its first read to after its journal commit. Every kernel process on the same filesystem contends for the same lock, so two kernels cannot interleave on one store: the second waits up to `--lock-timeout` (default 10 s) and is then refused (`StoreBusyError`) having written nothing. Two competing assignments therefore cannot both compute the same fencing token, and cannot both persist an attempt: the one that holds the lock writes, the other re-reads the state afterwards and is refused because the task is no longer READY (`tests/test_lifecycle_kernel.py::test_two_competing_assignments_cannot_both_write`).
- **The undo log.** While it holds the lock the verb remembers the previous bytes of every path it writes (or that a path did not exist). If anything after the first write refuses (a compare-and-swap that finds the state file moved, a journal failure, any exception), every path is put back exactly as it was before the verb, in reverse order. A refusal therefore writes nothing even when it is discovered late (`::test_a_refusal_after_the_first_write_leaves_no_partial_record`, `::test_a_journal_failure_rolls_the_store_back_to_the_last_commit`).
- **The journal's preconditions.** A journaled verb runs only on a clean checkout, checked under the lock before its first write (`journal_preconditions`): nothing may be staged anywhere in the checkout (a staged change inside the store would be lost to a rollback; one outside it means the checkout is being used for something else, and the kernel refuses rather than works around it), and nothing under the store may be modified or untracked (it would be swept into the commit as the verb's own). Either condition is a refusal that names the paths and writes nothing; the offending state is left exactly as found. With both true, the pre-verb index equals HEAD for the store, so a rollback to HEAD is a rollback to the pre-verb index (`::test_the_journal_refuses_a_checkout_with_staged_or_uncommitted_state_before_writing_anything`, a real repository: a staged file outside the store, an edited store file, a stray file under the store, then the clean commit carrying only `engineering/`). The porcelain is read NUL-terminated (`-z`), and the one exempt path is exactly `<store>/.kernel.lock`, the layout's own; a stray file merely named like it, at the store root or below, is uncommitted state and refused (`::test_a_stray_file_named_like_the_lock_is_not_exempt_from_the_journal_preconditions`). The store is therefore a dedicated checkout by mechanism, not by convention.
- **The commit is scoped to the store.** The journal stages the store and commits with the store as its pathspec (`git commit -- <store>`), so the commit records the store's paths and nothing else. Index state that another process stages while the verb runs, after the precondition held, can neither enter a kernel commit nor be consumed by it: it stays staged exactly as that process left it, and the next verb's precondition names it (`::test_the_journal_commit_is_scoped_to_the_store_so_a_change_staged_mid_verb_is_neither_committed_nor_consumed`, a real repository with the seam staging an outside file between the check and the commit). A kernel commit carries only the kernel's writes by construction, not by timing.
- **The index is inside the boundary.** The journal stages the store (`git add -A -- <store>`) and commits. If either step fails, the journal first puts every index entry under the store back to HEAD's (`git reset HEAD -- <store>`, which under the preconditions above is the pre-verb index) and then raises `JournalError`, after which the undo log restores the files. Working tree, index and HEAD are then what they were before the verb, and nothing attempted stays staged (`::test_a_journal_commit_failure_after_staging_leaves_tree_index_and_head_as_before`, a real repository whose pre-commit hook refuses). The CLI reports it as `JOURNAL FAILED` (exit 3), distinct from a refusal (exit 2).
- **Checks before writes.** Each verb performs every check it can (identity, stage, token, lease, base, evidence, scope, eligibility, the current state's `transition_seq`) before its first write; the compare-and-swap at the end is the last check, and under the lock it can only fail if something outside the kernel wrote the state file, which the undo log then makes harmless.

What this does not do: the lock is a filesystem lock, so it serialises every kernel on one host or on one shared filesystem, not two hosts holding separate clones of the state branch. Across hosts the discipline is the branch itself: the journal is pushed fast-forward only, so a kernel whose clone is behind cannot publish without first integrating the other host's commits, and every record identity is immutable, so two hosts writing the same task produce a visible conflict, never a silent overwrite. A store is written from one clone at a time; that is an operating rule, stated here, not something the kernel can enforce from inside one clone.

## Verbs and their fences

Each verb validates everything, then writes. A refusal writes nothing and exits 2.

| Verb | Requires | Records | Stage after |
| --- | --- | --- | --- |
| `task` | base SHA is a commit; revision N-1 exists, is not owner-gated (status OWNER_GATE, `owner_gate`, or blocker class OWNER_ONLY) and has no live attempt; a revision blocked on a transient or deterministic blocker may be superseded, an owner-gated one never | task, state seq 0; the previous revision becomes OBSOLETE | READY |
| `assign` | READY or REJECTED; worker workspace at the task base | attempt (token = max token for the task + 1, lease), `opened` | ASSIGNED |
| `ack` | ASSIGNED; the attempt's token; the attempt's base | `acknowledged` | RUNNING (rendered BUILDING) |
| `heartbeat` / `--progress` | current attempt; token; lease not expired | `heartbeat` / `progress`; the lease renews from the event time | unchanged |
| `evidence` | RUNNING; token; lease | `evidence` with name, sha256, path | unchanged |
| `candidate` | RUNNING; token; lease; no candidate yet; SHA is a commit descending from the base; every claimed evidence name was recorded; every required evidence is claimed; with `--verify-remote`, the remote target branch resolves to the SHA; the changed paths are read from the repository with rename and copy detection off (`git diff --name-status --no-renames`), so a moved file counts as its source and its destination, and a declared set, when given, must equal them exactly | result (changed paths from git), `candidate` | EVIDENCE_READY |
| `dispatch` | EVIDENCE_READY; reviewer registered with `may_review`; reviewer principal differs from the author principal; the continuation policy allows review (branch head equals the candidate, scope, evidence) | dispatch + packet bytes, `review_dispatched` | REVIEWING |
| `verdict` | REVIEWING; no accepted verdict yet | admission + verdict bytes; on ACCEPTED also an acceptance and `accepted` | ACCEPTED, REJECTED, or unchanged when refused |
| `integrate` | ACCEPTED with an acceptance record; integration SHA is a commit; the accepted SHA and the target base are its ancestors; the target ref resolves to it (the remote's with `--verify-remote`, else the local ref); a fast-forward lands exactly the accepted SHA; anything else (a merge, a squash, a rebase) is refused unless the integration SHA is itself an accepted candidate of a task built on the target base, reviewed at that exact SHA, whose revision is still that task's latest, whose state is ACCEPTED or DONE and whose accepted attempt is its current one; the record names that acceptance | integration, `integrated` | DONE |
| `cancel` | a live attempt | `cancelled`; the token is dead | READY |
| `block` / `resume` | a non-terminal task that is not owner-gated: an owner gate can be neither re-blocked nor resumed by this kernel (nor cancelled nor superseded); it stays until a trusted owner authority adapter exists | `blocked` / `resumed`; resume recomputes the stage from the records, the latest admitted verdict first: an admitted READY is ACCEPTED, an admitted REPAIR_REQUIRED is REJECTED and stays so, a refused verdict decides nothing, then dispatch, candidate, acknowledgement | BLOCKED or OWNER_GATE / recomputed |
| `gate` | an owner-gated task | nothing; prints the gate as a proposal (payload, proposal id, fingerprint) for the owner layer to judge | unchanged |
| `verify-judgment` | an owner-gated task, `--owner-judgment <id> --owner-ledger <path>` | nothing; reports whether the judgment binds to the gate (in the ledger and uncorrected; made by a principal registered with the owner role in a named session; about exactly this gate, task, revision and attempt; APPROVED) and that its origin is not trusted (`origin_trusted: false`, `lifts_the_gate: false`) | unchanged |

The verdict outcome is one of three and all three are recorded: **accepted** (every fence held and the verdict is READY), **rejected_by_verdict** (every fence held and the verdict is REPAIR_REQUIRED; the task becomes REJECTED and a correction is a new attempt or a new revision), **refused** (a fence failed: observed or current SHA drift, task or attempt drift, author provenance drift, evidence fingerprint mismatch, reviewer ineligible under `evaluate_review_eligibility`, reviewer not the dispatched principal, reviewer not registered). A refused verdict changes no stage. The author identity in the verdict record comes from the attempt, never from the caller.

## Invariants kept

- **Immutable candidate identity.** One candidate per attempt; a correction is a new attempt with a higher token, or a new revision at a new base. A verdict about one SHA never carries to another.
- **Fencing.** Every worker write carries the attempt's token; a stale token, a superseded attempt or an expired lease is refused. Late results cannot become authoritative.
- **Reviewer independence.** Dispatch refuses the author principal and unregistered principals; admission re-runs the eligibility rule on the reviewer's declared session and workspace at the exact SHA. Nothing here relaxes `Ineligibility`.
- **Scope is a repository fact.** A candidate's changed paths come from `git diff` between the attempt base and the candidate with rename and copy detection off, so a move touches both its source and its destination; the worker may declare them only to be checked. The continuation policy's `allowed_paths` gate therefore inspects the diff, and an out-of-scope file left out of a declaration is a refusal at `candidate`, or a refused dispatch when nothing was declared.
- **Owner authority.** Acceptance is engineering READY only. `owner_gate` and `OWNER_GATE` are recorded, never resolved by the kernel. An owner gate stays an owner gate: the kernel refuses to lift, cancel, re-block or supersede it, because it cannot verify that an owner judgment came from the owner. A ledger file anyone can write proves content, not origin, and no owner-ingress artifact with verifiable origin exists in this repository; a git author or committer string is likewise self-asserted. What the kernel preserves is the binding contract a trusted owner authority adapter will build on: `gate` says what an owner judgment must be about, and `verify-judgment` checks that a `JudgmentRecord` (`app/actions/judgment.py`, the same record and ledger the owner's decisions already use) is in the owner's ledger and uncorrected, was made by a principal registered with the owner role in a named session, judges exactly this gate, task, revision and attempt, and is APPROVED, while reporting that origin is not trusted. `OwnerResolution` is the record such an adapter would write; nothing here writes it. Nothing deploys.
- **A merge is not the accepted SHA.** COMPLETE follows only from landing exactly the accepted SHA (fast-forward), or from landing an integration result that was itself recorded, reviewed and accepted as a candidate at its own exact SHA, and whose acceptance is still authoritative (latest revision, ACCEPTED or DONE, current attempt); the integration record names that acceptance. A superseded or withdrawn candidate's acceptance is history.
- **A rejection stays a rejection.** Block and resume recompute the stage from the latest admitted verdict; a rejected candidate never returns to REVIEWING, only a new fenced attempt or revision can be reviewed.
- **One writer, whole records.** See above: the writer lock and the undo log make "a refusal writes nothing" a mechanism.
- **Restart safety.** Stage, lease and history are derived from files on every call; a fresh kernel on the same root gives the same answers.
- **COMPLETE only from evidence.** The projection reports COMPLETE only when the state is DONE and both the acceptance and the integration records exist and agree; a DONE state without them is UNKNOWN.

## What the projection does with it

`config/agent_roster.json` may declare `engineering_store`. When it does, `scripts/agent_state_view.py` reads the records first: a worker with a current assignment is ASSIGNED, BUILDING (lease alive), STALE (lease expired), IDLE (holding a task that is under review, accepted or rejected), BLOCKED or OWNER_GATE from the record; a principal with an open dispatch is REVIEWING; a worker whose task reached COMPLETE reads COMPLETE for one stale window. The process and git probes still run and may only disagree aloud, in `reconciliation`, which the environment shows. With no record, the probe decides as before. A roster entry may use `probe.kind: records_only` for a worker nothing on the host can observe (an external reviewer): UNKNOWN unless a record places it.

## Declared, not verified

- The reviewer's session and workspace facts at verdict time are declared by whoever relays the verdict; the kernel records and evaluates them, it cannot inspect a reviewer's machine.
- Worker identity is what the kernel recorded at dispatch (a controller-issued fact), but processes are not bound to it cryptographically; the Phase 1 limitation in ENGINEERING_CONTROL_PLANE_VNEXT.md §6 still stands.
- The store is written by one kernel at a time on one filesystem (the writer lock) and by one clone at a time across hosts (the branch's fast-forward discipline, an operating rule the kernel cannot enforce from inside one clone; see "One writer, whole records").
- The owner's ledger is a file the owner layer writes (JSON lines of `JudgmentRecord`s; `judgment_to_dict` is the line format, `load_judgment_ledger` reads it through the ledger's own invariants). The kernel verifies a judgment's binding to the gate and its provenance fields against the registry; it cannot verify who wrote the file, and therefore does not act on it. Lifting an owner gate needs a trusted owner authority adapter that establishes origin; until one exists, owner gates are unresolvable here.

## Backfill

A record may carry a time in the past only with `backfilled: true` and an `evidence_ref` naming what it was taken from (a commit, a CI run, a verdict text). Both the event time and the recording time are kept, and the projection flags the task as backfilled. Nothing backfilled is ever presented as live.
